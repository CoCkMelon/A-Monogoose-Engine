File: text.txt - text rendering

GOAL
Real, good-looking text rendering that works in both the desktop and
web builds from one C implementation, feeds the same batch renderer
as sprites (render.txt), and is crisp at any size or rotation.
Serves UI, HUD, and the dialogue typewriter (dialogue.txt).

WHY THIS IS HARD / WHAT BROKE BEFORE
  - attempt 1's engine shipped a "stroke font" (stb_easy_font):
    ugly, no antialiasing. The game had to hack around it by
    rasterizing each string with SDL_ttf into a texture every time
    text changed.
  - attempt 2 had no text at all.
  - The single-header font libs were also a compile problem
    (include/OOM pain, fragile in a mixed C/C++ tree). "Good" here
    must mean: the engine's own text module compiles clean with
    warnings-as-errors and is included from exactly one place; any
    vendored rasterizer lives in third_party/ and is exempt from
    -Werror (build.txt rule 3).

DECISIONS (from the requirements)
  1. TEXT RENDERS FROM BAKED GLYPH ATLASES (rasterized glyphs
     baked into atlas textures), drawn as textured quads through the
     shared batch (render.txt). This is the baseline: simple,
     reliable, works in pass 0. Distance-field text (DSDF) got its
     OWN pass later (faces, below); it never replaced the atlas.
  2. Text becomes MESH geometry. Each glyph quad (from the atlas
     texture) is tessellated using per-glyph metrics; glyph quads are
     packed into the shared sprite/mesh batch alongside everything
     else, so text stays in the SAME single pass/batch where possible
     (render.txt rule 5, ui.txt). This mesh design is what lets text
     work in 2D AND 3D from one code path: each glyph quad is placed
     by a pose (a 2D x/y or a 3D position + orientation), so the same
     layout feeds both.
  3. DSDF IS OPTIONAL, decided by implementation quality - and it
     has been ADOPTED as an optional third face (faces, below), with
     its own DSDF pass (render.txt). The atlas faces stay the
     default and the baseline; DSDF is for callers that want
     resolution-independent edges and accept the extra pass.
  4. The atlas + glyph data can be built EITHER at startup OR at
     build time. Prefer BUILD TIME: a host tool rasterizes the font
     once and emits plain C arrays (atlas pixels + glyph metric
     table) baked into the binary. Deterministic, zero startup cost,
     identical on native and web. A startup path is an allowed
     fallback for fonts not known until runtime.
  5. The baking/rasterizer tool may be written in a language with
     compile-time power (a C++ constexpr generator, or a small
     Python tool) because that simplifies generating the tables.
     What matters is the OUTPUT: plain C data arrays the C23 engine
     reads. The in-engine side stays C23; if a runtime rasterizer is
     ever needed in-engine, it lives in the single allowed C++ shim.
     This host tool is BUILD-TIME ONLY - it is never linked into the
     engine.

FACES (text_set_font; layout AND draw both run under the face)
  - PIXEL (default): Pixelify, nearest sampling, integer glyph
    sizes. The pixel-art face; also the FALLBACK: requesting a
    face whose atlas was never uploaded (text_init_hires /
    text_init_dsdf not called) is a no-op and the mode stays PIXEL,
    so layout metrics and draw can never disagree.
  - SMOOTH (default smooth face): DejaVu baked at 2x into a 2048
    coverage atlas, layout metrics divided back to 1x units. Draws
    as PLAIN quads through the default textured pass (bilinear, no
    shader reconstruction) - anti-aliased at any scale with zero
    extra passes. Init with text_init_hires().
  - DSDF (optional): DejaVu DSDF (R=distance, GB=gradient),
    decoded per pixel by the DSDF pass program. Crispest at extreme
    scales/rotations; the caller creates the DSDF pass
    (AME_RP_PASS_DSDF) and begins it around the text. Init with
    text_init_dsdf().
  GRID CONTRACT: glyph origins and the laid-out width snap to the
  pixel grid (integer values) in EVERY face, so text never shimmers
  between faces or frames. Tests assert this per face.

FONT SOURCE
  - Bundle the font bytes as data (Pixelify for PIXEL, DejaVuSans
    for SMOOTH/DSDF). For pixel-art 2D, nearest sampling and
    integer glyph sizes. The SMOOTH face is the softer choice at
    draw (bilinear over 2x cells); the DSDF face replaces
    texture-filter crispness with a shader edge (decision 3).
  - Unicode: UTF-8 input. The atlas covers the needed codepoint
    ranges (latin, latin-ext, cyrillic, plus a fallback). A missing
    glyph renders as a visible fallback box, never a crash.

WHERE TEXT LIVES (2D and 3D)
  Text can be placed in three ways from one layout engine:
    - SCREEN/UI text: stays in front, in the UI layer. Used by HUD
      and dialogue boxes.
    - WORLD labels: placed at a world point/pose. In 3D, BILLBOARD
      mode keeps the glyph plane facing the camera so text is always
      readable (name tags, floating hints). In 3D, PLANAR mode lays
      the text flat on a surface (wall signs, decals) via its pose.
    - In 2D, world labels are just text at a world x/y, same as any
      in-scene mesh (ui.txt says UI is in-scene meshes).
  The layout math is identical for all; only the pose differs. Keep
  the billboard "face camera" and planar "apply orientation" as two
  pose helpers, not as separate text systems.

TEXT PIPELINE (order)
  decode utf-8 -> runs (inline styles) -> layout (wrap/align) ->
  glyph list (index + position, with kerning) -> submit glyph quads
  to the batch.

FEATURES REQUIRED IN V0 (full scope was requested)
  - Word wrap to a box width.
  - Horizontal alignment: left, center, right. Vertical: top, center.
  - Per-string color tint and scale.
  - Inline rich tags in the string for runs, for example a color,
    a size change, and a pause used by the typewriter:
        {c=FFD700}gold{/c}, pause {p=0.5}
    The exact tag set is defined by the layout parser; it must be
    small, plain, and case-insensitive.
  - UTF-8 / Unicode text (not limited to ASCII).
  - Typewriter reveal for dialogue: the layout yields an ordered
    glyph list, and a reveal amount 0..1 (or a glyph index) hides
    glyphs beyond it so the UI can type out text over time.

API SHAPE (text.h, extern "C")
  Layout and drawing are two steps so the UI can measure before it
  draws (needed for centering and dialogue boxes).

    text_init()                 load baked PIXEL atlas + metrics
    text_init_hires()           upload the SMOOTH (hires) atlas
    text_init_dsdf()            upload the DSDF atlas
    text_set_font(face)         PIXEL / SMOOTH / DSDF (no-op fallback)
    glyph info lookup per codepoint

    measure(text, box_w) -> width, height, glyph count   (no draw)
    layout(text, box_w, align) -> an array of positioned glyphs
    draw_ui(layout, x, y, scale, tint)      // screen/UI position
    draw_world(layout, pose, scale, tint)   // world pose; billboard
                                            // or planar via pose mode
    reveal controls feed draw a hidden-glyph count for typewriter.

  The text module knows nothing about gameplay; it just places
  glyphs. The dialogue UI (a gameplay concern) owns a text box, a
  box width, an alignment, and a typewriter timer.

QUALITY BAR
  - Text is crisp at integer and, where possible, at non-integer scale
    and rotation from the atlas (bilinear/trilinear filtering), not
    the blurry per-string-raster problem of the past.
  - Thin strokes in small sizes do not vanish. The v0 atlas handles
    common cases; if very small/colored-thin glyphs need a crisper
    edge, that is the moment DSDF is reconsidered (decision 3) - it
    is optional, not required at v0.
  - Deterministic: the same string + font + settings lays out the
    same on native and web (byte-identical glyph positions).

COMPILE / TEST REQUIREMENTS (fixes the past problems)
  - The font code is included from exactly ONE translation unit.
    No fragile single-header that is force-included or doubled.
  - Warnings-as-errors in CI on the whole tree including this module.
  - A test renders a known string and compares glyph count,
    positions, and width against a golden expected value.
  - A headless layout test needs no GL (layout is pure CPU); only
    the final draw needs GL. Keep layout and draw separable so text
    logic is unit-testable without a window.

BANNED
  - The old per-string-texture approach (rasterize every change).
  - A separate 2D text and 3D text system (one mesh/layout engine).
  - Depending on DSDF/SDF as a v0 requirement (atlas is v0; DSDF is an
    optional later upgrade, decision 3 - do not let a fragile SDF
    implementation block shipping text).
  - Depending on a font lib that must be force-included or that
    breaks the build; any vendored rasterizer is used from one TU
    and compile-tested.
  - A separate text renderer for web (same C, shared by Emscripten).
  - Blocking font work in the audio callback or per frame.
  - Any allocation per frame in the layout/draw hot path.

CHECK
  A UI example draws a wrapped, centered, colored line and a
  Cyrillic line; both are crisp at 1x and 3x and when rotated.
  The dialogue box types out with a typewriter reveal.
  Layout tests pass headlessly; compile is clean with
  warnings-as-errors; native and web match.
