ame-next ENGINE SPEC
File: render.txt - drawing

GOAL
Fast drawing in very few GL draw calls for BOTH a 2D mode (batched
sprites/tiles, pixel-perfect camera) and a 3D mode (meshes under a
3D camera). One renderer and one shader set serve both. Native and
web share the GLSL.

ARCHITECTURE - PASSES (v1: multipass, decided - see note after rule 5)
  The renderer is a small set of PASSES over one shared batch core.
  rp_init creates exactly ONE pass: the default textured pass (pass
  0) - a single branchless textured program (tint * tex, layer depth,
  optional blend). It draws world + in-scene UI + text together,
  exactly the v0 single-pass picture. Everything beyond that is an
  APP-CREATED pass:
    - LIT: forward lighting (1 dir light + ambient + 1 point light)
      with per-push lit/unlit stamps and normals. Lit pixels get the
      Lambert term; unlit pixels are bit-identical to pass 0.
    - SHADOW: a depth-only re-draw of the lit batch through an ortho
      light camera (3x3 PCF, slope-scaled bias). Removes only the
      diffuse direct term inside shadow; with shadows off the output
      is bit-identical to the no-shadow path.
    - POST: scene renders into an offscreen RGBA8 target, then one
      fullscreen triangle composes it (tint multiply + vignette).
    - DSDF: the DSDF text program (text.txt); text glyph quads pushed
      while a DSDF pass is current decode the DSDF atlas per pixel.
  rp_pass_create(&desc) creates a pass and returns its id;
  rp_pass_begin(&frame) makes a pass current; every push targets the
  current pass. The current pass persists across frames (no implicit
  reset). Passes are a setup-layer choice (principles): the app
  creates the passes it needs at init, then draws.

SHADERS - SEPARATE MODULAR FILES
  GLSL lives in shaders/*.glsl - one small module per file
  (textured.vert/frag, lit.vert/frag, dsdf.vert/frag,
  shadow_depth.vert/frag, post.vert/frag, plus shared chunks under
  shaders/common/ included with #include "file.glsl"). A host tool
  (tools/bake_shaders) bakes them into generated/shaders_gen.c at
  build time; the baked table is what ships, so native and web run
  the SAME sources. render.c contains NO inline GLSL: it resolves
  #include lines against the baked table, compiles each pass
  program once at creation, and never touches GL state outside the
  batch/pipeline module. GLSL ES subset only (rule 1): one shader
  set for desktop GL, GLES, and WebGL2.

API SHAPE - ONE STRUCT POINTER
  Every pass/push/state function takes exactly ONE pass-by-pointer
  struct (ame_rp_* in render.h, extern "C"):
    rp_init(&desc)              stepwise builder: begin/clear/size/
                                camera/blend; creates ONLY pass 0
    rp_pass_create(&desc)       -> pass id (LIT/SHADOW/POST/DSDF)
    rp_pass_begin(&frame)       make a pass current for pushes
    rp_push_sprite(&s)  rp_push_quad(&q)  rp_push_tri(&t)
    rp_push_mesh(&m)            Assimp-baked verts (levels.txt)
    rp_lighting(&l)  rp_point_light(&l)    arm the LIT pass
    rp_shadow(&s)               arm the SHADOW pass for this frame
    rp_post(&p)                 tint + vignette for the POST pass
    rp_begin_frame() / rp_end_frame()      upload, draw, present
  Scalar stamps stay scalar (rp_set_lit, rp_set_normal): one
  parameter needs no bundling. Push functions append to a buffer
  that is rewritten in place each frame (never reallocated).

RULES
1. ONE renderer, ONE shader set.
   Desktop (POSIX + Windows) = OpenGL core via a loader. Web =
   WebGL2 via Emscripten. Android = OpenGL ES via SDL/EGL. Use
   shared GLSL (GLSL ES subset) for all three, so the same
   shaders/VAO/texture path runs on desktop GL, GLES, and WebGL.
   NO second renderer for any target.
   The build dimension macro (AME_2D / AME_3D, see principles)
   picks which camera + vertex path is active, not a separate
   engine.

2. Batch sprites/tiles into one dynamic vertex buffer.
   Group by texture page, sort by page then layer.
   Aim for ONE draw call per frame when everything is on one atlas.

3. Nearest sampling for pixel art. Atlas pages have at least 2px
   padding so edges do not bleed. (The hires text face is the
   deliberate exception: 2x coverage cells sampled bilinear
   through the plain textured pipeline - text.txt.)

4. Pixel-perfect camera: integer-snapped position, integer zoom
   steps only, glViewport set on init and on every resize.

5. Pass 0 stays SINGLE-PASS: each frame is clear, then batch
   submissions per pass. All drawing goes through the
   batch/pipeline module. No scattered glDraw calls from random
   files. Multipass (app-created LIT/SHADOW/POST/DSDF passes) was
   the deferred decision - it is decided now (see ARCHITECTURE):
   the default stays one clear + one batch + present, and each
   extra pass is explicit, created by the app, and bit-identical
   to pass 0 when its effect is off.

6. 2D AND 3D MODES share the renderer.
   - 2D mode: pixel-perfect camera (integer-snapped position,
     integer zoom steps), sprite/tile batch (rule 2), nearest
     sampling (rule 3). This is the 2D pixel-art path.
   - 3D mode: a 3D camera (position + look + projection), a mesh
     pass with per-object world matrices, depth on, lighting via
     the LIT pass. The engine renders with its OWN GL pipeline (no
     external render lib such as sokol) so there is one renderer
     for both.
   - UI and text are in-scene geometry in both modes (ui.txt,
     text.txt). Billboards/planar text and the UI layer are pose
     features of the same mesh path, not a second renderer.

VERTEX FORMAT
  2D: position x,y / uv u,v / color rgba / layer
  3D: position x,y,z / normal / uv / color rgba / layer
  Push functions append to a buffer that is rewritten in place each
  frame (never reallocated). The batch and pipeline code is shared;
  only the vertex layout + camera + shader are chosen by dimension.

BUILDERS
The pipeline/camera/pass setup is a setup-layer builder (see
principles). The per-frame vertex buffer is hot state: one owned
buffer, updated in place, not wrapped in per-draw objects.

TEXTURES
Small integer ids into a static texture registry loaded once.
No creating textures per frame, no leaks. comps == 1 uploads as
COVERAGE (white RGB + coverage alpha, CPU-expanded); comps 3/4 are
RGB/RGBA.

EXAMPLE API (render.h, extern "C")
  ame_rp_desc d;
  rp_desc_begin(&d); rp_desc_clear(&d, ...); rp_desc_size(&d, w, h);
  rp_desc_camera(&d, &cam); rp_init(&d)   // pass 0 only
  ame_rp_pass_desc litd = { .kind = AME_RP_PASS_LIT };
  int lit = rp_pass_create(&litd);
  ame_rp_pass_frame lf = { lit }; rp_pass_begin(&lf);
  rp_push_sprite(&(ame_rp_sprite){ .tex = t, .x = x, ... });
  rp_end_frame()       upload verts, draw ranges, present
  rp_load_texture(pixels, w, h, comps, nearest)

BANNED
  - Rebinding programs/buffers per sprite (kills batching).
  - New vertex buffer each frame; silent overflow (assert or drop).
  - GL calls scattered across gameplay code.
  - Inline GLSL in C files (shaders live in shaders/*.glsl).
  - A second GLSL / renderer for web.
  - A separate 2D renderer and 3D renderer with no shared layer.
  - Many independent texture binds when one atlas would do.
  - Multi-parameter push calls (one struct pointer, see API SHAPE).

CHECK
  A 2D build renders 1000 sprites in a handful of draw calls with a
  pixel-perfect camera; resize/camera-follow keep pixels aligned.
  A 3D build renders a mesh scene under a 3D camera, with in-scene
  UI and world labels on top, in few draw calls. Both builds use the
  same renderer core. Native and web look the same. No texture/
  buffer leaks across many resizes. rp_init alone draws the v0
  single-pass picture; each extra pass is off-by-default
  bit-identical when disarmed.
