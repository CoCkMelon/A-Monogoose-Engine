ame-next ENGINE SPEC
File: plan-3d-puzzle.txt - campaign F: 3D third-person puzzle game

WHY THIS FILE EXISTS
The engine has a proven 3D render path but no way to get an AUTHORED
3D scene or an ANIMATED CHARACTER into it. This file records the
decisions, the measured gap, the work packages and the turn budget for
closing it, so the work is not re-decided per session and so no agent
starts a second scene pipeline beside this one.

GOAL
A third-person 3D puzzle game on trunk: one animated human character,
levels authored in Blender, playable as an example game, proven on
desktop first and then on the other three targets.

=====================================================================
DECISIONS LOCKED (2026-11-18, with grounds)
=====================================================================

1. glTF/glb IS THE SOURCE FORMAT, AND THE PATH IS BAKE-ONLY.
   Grounds, in order of weight:
   - OBJ cannot carry a skeleton, skin weights, animation clips or a
     node hierarchy. levels.txt already names this as the cue to move
     to glTF or the bake path, and already forbids Assimp in the game
     binary ("CI, web/WASM and release builds ship cooked data only").
     Bake-only is therefore the RECORDED spec, not a new deviation.
   - No runtime glTF parser means no parser code in the APK/web
     binary, no startup parse cost, and one less vendored dependency
     in the pure-C engine. The 2026-11-11 deprioritization of glTF
     import is lifted for this campaign on that new ground: a skinned
     animated character is not reachable any other way.
   - Iteration cost is the trade, and it is bounded: one command
     re-bakes (tools/), ninja rebuilds only the generated TU, and
     STATIC geometry may still iterate through the existing runtime
     OBJ path (levels.txt DEV path, unaffected by this decision).
     Measure bake+rebuild; if it exceeds ~30 s per change, record the
     number here and revisit.

2. CHARACTER MOTION IS KINEMATIC, ON THE EXISTING GEOMETRY MODULE.
   Grounds: physics.txt settles v0 as geometry-only - intersections,
   raycasts, mesh->primitive proxies, broad-phase - with actors moving
   themselves in the fixed step and NO solver. Trunk's geometry module
   already implements that spec (789 lines: AABB, sphere, segment,
   capsule, OBB, ame_geo_raycast, ame_geo_ray_shape,
   ame_geo_overlap_world, ame_geo_add_mesh_proxies, uniform-grid
   broadphase 16^3 in 3D). A capsule character controller (sweep,
   move-and-slide, ground probe, step-up, slope limit, gravity) is
   assembly on top of it, not a new dependency and not a spec change.
   Measured donor fact: the B-rewrite's phys module (497 lines) is 2D
   biscuit VEHICLE code (ame_phys_plat, ame_phys_seg, circle_segs,
   wheel, strut_forces) - it is NOT a donor for 3D character motion.
   Rigid-body props (stacking crates, joints) stay OUT of scope; they
   would reverse the settled no-solver spec and need their own case.

3. SKINNING IS CPU-SIDE FIRST.
   Grounds: one character, so the per-frame cost is a few thousand
   transformed vertices - measurable, and cheap next to the batch
   renderer's own work. CPU skinning writes plain ame_mesh_vert into a
   scratch buffer that rp_push_mesh already accepts, so render.c,
   mesh.h and the shader set stay UNTOUCHED. That also de-conflicts
   this campaign from the frame-independence work currently editing
   render.c and text.c. GPU skinning (bone-palette UBO + a shader
   variant + batcher changes) is deferred until a measurement says the
   CPU path misses the frame budget; budget for it separately.

4. BAKED OUTPUT IS CHECKED IN, AND BAKING IS CI-VERIFIED.
   The generated scene/skeleton/clip C files live in generated/ (the
   pattern font_atlas*.c already sets), so a normal build needs no
   libassimp. libassimp-dev (5.4.3) is already installed by CI
   (.github/workflows/ci.yml), so CI can re-bake a checked-in fixture
   and diff it against the committed output - a reproducibility gate
   that catches a stale or hand-edited generated file.

5. SKIN DATA IS A PARALLEL STREAM, NOT A NEW VERTEX FORMAT.
   ame_mesh_vert stays float[8] (pos/nrm/uv) - it is shared by the OBJ
   loader, assimp2c and rp_push_mesh, and changing it would ripple
   through every consumer. The baker emits joints and weights as
   separate const arrays indexed by vertex; the skinner reads both and
   writes ame_mesh_vert.

WHAT ALREADY EXISTS (measured 2026-11-18 on trunk 71c4633)
=====================================================================
Render: perspective camera (camera_persp3d); pass system with LIT
  (directional + point + ambient, shadow receive), SHADOW (depth-only
  caster pre-pass over a source pass), POST/CUSTOM/DSDF; rp_push_mesh
  with a per-draw column-major 4x4 xform, tint and layer; directional
  shadow-map module. AME_3D is a per-target compile switch.
Geometry: the physics.txt v0 query layer, 789 lines, dimension-generic
  via AME_DIM (see decision 2).
Scene authoring spec: levels.txt already fixes the conventions this
  campaign must REUSE, not reinvent - collider kinds inferred from
  object names (BoxCollider, CircleCollider, EdgeCollider,
  ChainCollider, MeshCollider), markers as kind-prefix + stable id
  (P_, E_, T_, S_, G_, C_, K_col_), the 63-byte Blender name cap, rich
  tunables in a sidecar and/or a generated header (scene_ids.h,
  scene_vars.h), integer ids at runtime (no per-frame string lookups),
  one tuning config header, per-level deterministic seeds. Sidecars
  are TOML per the 2026-11-14 format decision.
Also available: events (overlap-edge + deferred queue, test_events 72),
  prefab (name -> spawn -> handle, test_prefab), dialogue (runtime
  libfyaml + dlg2c bake, test_dialogue), particles, positional audio
  (audio_pan, audio_ray), time (ame_time_*), declared loop policy
  (app_fixed/app_step + ame_loop_desc), input with gamepad/touch/
  sensors, text/HUD, and native/Android/web/Windows CI.

WHAT IS NEW (nothing exists on any of the three attempts)
  glTF import (host-side) - scene graph, skeleton, skin weights,
    animation clips, materials. tools/assimp2c is 95 lines today and
    emits one mesh's pos/nrm/uv + indices only.
  Runtime scene module - baked tables into pools, node hierarchy,
    world matrices, name -> prefab spawn.
  Skeleton + animation runtime - bone palette from clips, sampling,
    blending, state machine, CPU skinning.
  Character controller, third-person camera (spring arm + occlusion).
  Measured donor fact: the B-rewrite contains ZERO files matching
  skeleton/anim/gltf/skin/scene - there is no donor for any of this.
  Component/behaviour layer (campaign F2, docs/components.txt): visual
    components in pools, name-bound from baked scene data, one engine
    draw system, behaviour as registered C function tables. No donor
    exists for this either - attempt 1's cpp/unitylike is a C++ facade
    on flecs and is archive.

=====================================================================
CAMPAIGN F2 (2026-11-18): COMPONENT-DRIVEN VISUALS - spec components.txt
=====================================================================
Recorded requirement: the MAJORITY of visuals - entity/scene visuals
AND HUD/UI/text - are defined by data and behaviour tables, not by
hand-written immediate-mode draw calls in app_render. Stated as
"monogoose behaviour script", after attempt 1's MongooseBehaviour.

Decisions, with grounds:
- TRUNK-NATIVE SHAPE. Data in fixed pools + explicit tables of plain C
  functions, registered at startup; no per-entity vtable, no
  GameObject class, no reflection, no script VM, no ECS, C-only.
  principles.txt CORE IDEA 2 and the agents.txt forbidden item both
  stand; the boundary (DATA + EXPLICIT TABLES, never OBJECTS +
  VIRTUAL DISPATCH) is now written into both files so the next agent
  does not have to re-derive it. Measured: attempt 1's cpp/unitylike
  is 25 files / 178 KB of C++ on a flecs EcsChildOf hierarchy - the
  facade shape, archive, nothing ported.
- SCOPE = entities + HUD/UI/text. app_render becomes the exception
  path (full-screen passes, debug overlays, one-off draws).
- The explicit draw-target change is FOLDED INTO THIS WORK, not
  patched separately: a `pass` field on ame_rp_sprite / ame_rp_mesh /
  the text draw entry, an invalid pass failing loudly (the ae0e465
  rule), and all 68 rp_push_* call sites migrated in the same change
  set with a golden zero-diff proof. Measured ground for the change:
  the batch sort key is pass*8192 + tex*256 + layer (render.c:223,243)
  where tex and layer come from the push struct but pass comes from
  ambient S.cur_pass - so today a draw call cannot answer "which
  buffer am I in" from its own arguments.

 B2  Component pools + name-bind tables + tests, no drawing yet:

=====================================================================
RISKS, AND THE SPIKE THAT RETIRES THE BIGGEST ONE
=====================================================================
R1 Assimp glTF skin/animation fidelity (highest risk, earliest test).
   Bone naming, inverse bind matrices, extra exporter nodes, Blender's
   Y-up conversion and quaternion key interpolation are all places a
   baker silently produces wrong poses. SPIKE, as the first task of
   WP1: export a minimal Blender character (2-3 bones, one 10-frame
   clip) to glb, bake it, and print bone count, parent indices,
   inverse bind matrices and key counts; compare against Blender's own
   values. One turn, and it either validates the whole approach or
   moves the problem into the open before any runtime code exists.
R2 Iteration latency from bake-only. Mitigations in decision 1; the
   measured bake+rebuild time is recorded here when known.
R3 Generated-code volume: clips can emit large arrays. Quantize
   (16-bit positions/quaternions), strip redundant keys, keep output in
   generated/ (font_atlas_dsdf.c already sets the precedent at ~125k
   lines). Watch compile time of that TU.
R4 Sandbox rollbacks (~0.5-1 turn each, 18+ so far). Everything lands
   pushed and API-verified; the baker fixture and generated output are
   in the repo, so a rollback costs a rebuild, not the work.
R5 Contention with the frame-independence campaign in render.c/text.c.
   Avoided by decisions 3 and 5; WP4 is the only package that must
   wait.
