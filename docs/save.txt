ame-next ENGINE SPEC
File: save.txt - saving and loading games (YAML)

GOAL
Save and load game progress with YAML, using the same libfyaml
dependency as dialogue. YAML is good for this because it is
human-readable (easy to inspect a save, easy to diff after a change)
and libfyaml already gives a real parser/emitter.

WHAT TO SERIALIZE (keep it SMALL and durable)
  A save holds DURABLE, mostly-small state, NOT a full dump of the
  whole runtime every frame:
    - unlocked abilities / unlocks and permanent progress
    - inventory, pickups collected, dialogue flags (which scenes or
      choices have been seen/answered)
    - settings (input bindings, audio gains, quality)
    - current level id + a checkpoint/spawn point
    - the few entities the game wants to persist (player state,
      fuel/hp, collected flags) read out of the pools (data.txt)
  Anything big or derived (geometry/static-world internals, full
  entity lists, renderer state) is rebuilt on load from the durable
  data, not stored.

SAVING (emit)
  On save, walk the small set of durable state and emit YAML with
  libfyaml's emitter (fy_emitter / fy_document_create then emit),
  or build the string and fy_emit. Output is one compact YAML file.

LOADING (parse)
  On load, parse the file with fy_document_build_from_file, read the
  fields by path (fy_node_by_path), and feed them back into the
  durable state, then re-init the level and rebuild pools/spawns
  from it (see levels.txt). A missing or corrupt field falls back to
  defaults; a corrupt whole file is reported clearly and ignored, it
  never crashes.

DIMENSION
  Save content is written dimension-neutral where possible. Positions
  are stored as a list of numbers (2 in AME_2D, 3 in AME_3D), read
  back into the current dimension. The save layout does not change
  when switching dimension unless a position is actually present.

VERSION
  Each save has a version number. On load, a newer reader accepts an
  older save (migrate small deltas); an unknown NEWER version is
  rejected with a clear message rather than guessed at.

WHERE IT LIVES
  The save module (save.h / save.c) knows the durable-state format
  and uses libfyaml. It does not know gameplay logic beyond the
  fields it serializes; the game decides what is durable and provides
  read/write callbacks per field set. Same code on native and web
  (web stores the file in its filesystem/persistent storage shim).

BANNED
  - Dumping the whole geometry/static world or full pools to YAML.
  - A hand-rolled YAML writer/parser (use libfyaml).
  - Storing pointers or engine handles in a save (save only durable
    ids/names/indices that are stable across a rebuild).
  - A save that depends on game logic state it cannot re-init from.

CHECK
  Save after unlocking a few abilities and collecting flags, then
  load in a fresh run: unlocks, flags, fuel/hp and current
  checkpoint are restored; the level rebuilds correctly.
  The save file is readable YAML (open it in an editor).
  Corrupt/truncated save is handled cleanly (defaults + a clear log),
  never a crash. Same behavior native and web.
