WHY THIS FILE EXISTS
Recorded 2026-11-19: the deadline that shaped earlier estimates is
gone, so this pipeline optimizes for CORRECTNESS PER STAGE instead of
speed. The shape follows from that: every BUILD stage is followed by a
VERIFY stage run by a different agent, and MEASURE stages run wherever

=====================================================================
HOW TO INVOKE A STAGE
=====================================================================
Workflow decided 2026-11-19: every stage is run by a FRESH agent that
has no prior conversation and an empty sandbox. This block is therefore
self-sufficient - paste it, fill in <S#> and <TOKEN>, and nothing else
is needed. <TOKEN> is a GitHub token with push and issue-comment rights
on the repository; the human supplies it per invocation. It must never
be written into a file, a commit, a comment or a log.

  You are stage <S#> of the ame-next subagent pipeline. You start with
  no context: everything you need is in the repository or below.

  1. Get the tree. Anonymous read is enough:
       git clone --depth 50 -b ame-next-trunk \
         https://github.com/CoCkMelon/A-Monogoose-Engine ame
       cd ame && git submodule update --init --recursive
     If your sandbox already holds a checkout, do not trust it:
     compare HEAD against
       git ls-remote https://github.com/CoCkMelon/A-Monogoose-Engine \
         ame-next-trunk
     and reset --hard onto that sha BEFORE editing anything. Sandboxes
     are rewound without warning (26 recorded); a rewind also wipes
     installed packages, build/ and file exec bits, so afterwards run
     chmod +x tools/*.sh web/build.sh. Anything never pushed is gone.
  2. Install the build dependencies: the exact apt list is in
     AGENT_HANDOFF.txt under DEPENDENCIES (canonical copy). Then
       cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=RelWithDebInfo
       cmake --build build -j && ctest --test-dir build
     and note the baseline test count BEFORE you change anything. Your
     stage must never end with fewer passing tests than that baseline.
  3. Read, in this order: docs/agent-sequence.txt (RULES FOR EVERY
     STAGE, then AGREED BUDGETS, then YOUR stage brief),
     AGENT_HANDOFF.txt, docs/agents.txt, docs/principles.txt,
     docs/components.txt, docs/plan-3d-puzzle.txt, and the GitHub issue
     your brief names - including its latest comments. Issue #3 is the
     coordination hub.
  4. Execute your brief exactly: its SCOPE, its MUST NOT, its
     ACCEPTANCE, its PROOF. If your brief's premise turns out to be
     wrong, STOP and report the measurement in the issue instead of
     working around it.
  5. End green: build OK, ctest at or above the baseline, the sanitizer
     trees and goldens your brief requires, and
       tools/ci_drift_check.sh HEAD~1 HEAD
     printing "drift: ok". Then commit on YOUR OWN BRANCH and open a
     pull request into ame-next-trunk (recorded 2026-11-20: every stage
     gets a branch + PR; the verify stage checks it and merges it, so
     trunk never receives an unverified direct push):
       R=https://github.com/CoCkMelon/A-Monogoose-Engine
       A=https://x-access-token:<TOKEN>@github.com/CoCkMelon/A-Monogoose-Engine
       git checkout -b s<N>-<slug>            # off the remote tip
       git commit -am "<stage>: <what landed>"
       git push "$A" s<N>-<slug>
     Verify the branch sha through the API afterwards - push output
     alone is not proof, and a push made while HEAD was rewound has
     already published a stale tip once. The <TOKEN> goes in the push
     URL and the API header ONLY: never in .git/config, a credential
     file, a commit, a comment, a doc or a log.
  6. Open the pull request into ame-next-trunk, then post your stage
     report as a comment in your issue (<TOKEN> works for the API too),
     and set your stage's STATUS line in docs/agent-sequence.txt in the
     same commit as the work. The verify stage merges the PR; you do
     not merge your own.

RULES FOR EVERY STAGE
=====================================================================
1. The remote branch ame-next-trunk is the source of truth. Sandboxes
   are rewound without warning (26 recorded): fetch, compare the tip,
   and reset --hard onto the remote tip BEFORE working. Local commits
   that were never pushed are gone after a rollback.
2. Dependencies vanish with the sandbox. Reinstall list is in the hub
   (#3) and AGENT_HANDOFF.txt; from the baker stage onward it includes
   libassimp-dev (measured: with it, tools/assimp2c builds -
   "assimp 5.4.3"). Blender 4.3.2 is also installable headless, so
   fixtures are GENERATED BY SCRIPT (blender -b --python ...), never
   hand-made, and are committed.
3. Every stage ends: build OK, ctest green (32 or more, NEVER fewer),
   commit, push, and the remote sha verified by API. Push output alone
   is not proof; a push made while HEAD was rewound has already
   published a stale tip once.
4. Gates: a change touching include/ame/*.h must touch docs/ in the
   same commit; a NEW public header needs its own docs/<stem>.txt;
   every getenv("AME_*") in src/ must appear in docs/env.txt. Run
   tools/ci_drift_check.sh locally before pushing.
5. Justify objectively - measurement and technical merit, never
   ownership or authority (recorded 2026-11-14).
6. A VERIFY stage adds no features. It rebuilds from the remote tip,
   re-runs the previous stage's claims with the same commands, and
   either confirms them with numbers or files the defect in the issue.
   Fixing a defect it finds is in scope; growing scope is not.
7. Update this file: every stage has a STATUS line. The BUILD agent
   sets done in the same commit as the work; the VERIFY agent that
   checks it fills in the sha (done(<sha>)) once it has confirmed the
   merge, because the build agent cannot know its own merge commit
   before the merge happens (amended 2026-11-21 after S1, which shipped
   "STATUS done" with no sha and left the table unable to answer "which
   commit is that?").
8. Never run two stages that touch the same files concurrently. S10 is
   the only stage with tree-wide reach into render.c and every example;
   it gets the lane to itself.
9. No engine-side defaults (recorded 2026-11-18): configuration is
   struct values with every field named, and a call that cannot take
   effect fails loudly instead of silently doing nothing.

AGREED BUDGETS (human answers, 2026-11-19)
=====================================================================
The sequence needed two numbers before it could proceed, and a workflow
decision. All three are settled; they bind stages, they are not advice.

B1 STARTUP DATA LOAD: at most 1 SECOND.
   A game may spend up to 1 s reading its own authored data (levels,
   dialogue, settings) at startup before that data has to be pre-baked
   into the binary. Lenient on purpose: it keeps authored files editable
   and the rebuild loop short, which matters more than a fast splash.
   It is applied PER TARGET - desktop, armeabi-v7a and wasm are measured
   separately in S21, and a target that goes over budget bakes for that
   target only, with the number that forced it recorded in #8.
   Consequences: RUNTIME PARSING IS THE DEFAULT for level, dialogue and
   settings data, so S21 confirms a budget instead of choosing between
   two designs. This does NOT reopen bake-only glTF (decision of
   2026-11-14): that rests on parser size, validation and reproducible
   output, not on load time, so 1 s is not a ground for revisiting it.

B2 PER-FRAME CHARACTER MATH: at most 1 MILLISECOND.
   Skeleton pose plus vertex blending for animated characters has to fit
   inside 1 ms of a 16.7 ms frame. Strict on purpose: it leaves the
   frame for rendering, which is what the puzzle slice spends it on.
   Consequence, reversing campaign F's decision 3 on objective grounds
   (a 4-influence blend of a few thousand vertices is not expected to
   fit 1 ms on armeabi-v7a, and the phone is a required target): the
   SHIPPING path is pose on the CPU (bone palette) plus blend on the GPU
   - stage S15B. The CPU blend survives as a TEST ORACLE ONLY: it is
   what the GPU output is compared against, it runs headless with no GL,
   and it is not compiled into a game binary, so the runtime keeps
   exactly one skinning path. 1 ms is measured, not assumed: S15 records
   the oracle's cost, S15B and S28 record the shipping path's.

 LESSON across D14 and D15, and it generalises past this repo: a fix aimed at
   one platform is a CHANGE to every platform that shares the predicate.
   #ifdef _WIN32 is not "MSVC" - MinGW matches it too, and the two disagree on
   both which deprecations exist and which CRT symbols their runtime exports.
   Likewise a header vendored for one platform still has to resolve its OWN
   includes there, which a relative include from the .c file does not arrange.
   Both were invisible to every local check available when D11 and D12 were
   written, because Linux matches neither predicate. The cheap insurance that
   catches them: after adding a platform shim, compile the affected file under
   EVERY toolchain that shares the predicate, and for a link-time symbol,
   actually LINK something rather than only compiling it.
  A pattern worth naming, and the depth here is worth stating exactly because
  the first draft of this paragraph said "three layers" and was wrong: fixing
  one failure reveals the next defect behind it. The windows clang job alone
  ran SEVEN deep - sibling build dir -> host FreeType -> SDL3 config layout ->

  include path - and the windows-cross job then added an eighth (D14) caused by
  the fix for the fifth. macOS ran two (sibling build dir -> GL deprecation).
  A job that dies at configure tells you about exactly one defect, and a job
  that dies at compile tells you about exactly one more, so "the job is red" is
  never a count of the defects in it. Budget for the chain, not the head of it.
